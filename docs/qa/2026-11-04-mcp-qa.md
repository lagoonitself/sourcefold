# Sourcefold MCP QA — 2026-11-04 (Hermes)

Tested: remote connector `https://sourcefold-eight.vercel.app/api/mcp` (OAuth) — all 38 tools — and the
`.mcpb` v0.5.0 local server, with the desktop app closed and open. Test data lives in the project
"Hermes QA (safe to delete)" [d202b582-e33b-472e-a27c-7ada2fe2bcb3].

What works: browse/read (sections, parts, transcripts with timestamps), notes, highlights, tags/status,
outline/cards/b-roll/script export, remove_text + undo (remote, persisted), move/rename/delete dry runs,
cancel_waiting_links, merge_duplicates, add_image by URL, list_collection. Remote add_links saves cloud-

within ~1 min of being opened. Desktop agent API search/show work.

## Bugs, by severity

### P0-1 edit_note overwrites the text of ANY source (data loss)
`edit_note` with the id of a web page ("How to Do Great Work") replaced the whole article with
"should be refused" and reported success. The tool description says it only works on notes.
- `apps/mcp/src/tools/notes.ts` relies on the API answering "only notes", but
  `packages/client/src/routes/items/[id].ts` PATCH accepts `markdown` for every kind (it is also what
  `remove_text` uses, so the API itself can't simply refuse).
- Fix: in `edit_note`, fetch the item first and refuse unless `kind === "note"` (with the existing
  "use update_source" hint). Add a test. Optionally the API could require an explicit flag for non-note
  markdown writes.

### P0-2 The .mcpb can never use the desktop app's sign-in ("isn't signed in on this computer")
Two layers:
1. `apps/mcp/src/config.ts` `loadCredentials` reads `session.token` + `session.web_url` (pre-2026-10-23
   format). `apps/desktop/src-tauri/src/session.rs` now writes `access_token`, `supabase_url`,
   `publishable_key`, `expires_at`, `user_id`, `email`. So with no pasted token the extension always says
   not signed in, although the app is signed in.
2. Even with the field names fixed, the web REST API rejects the desktop JWT: `apps/web/src/lib/api.ts`
   `requireApiUser` only accepts `sf_` tokens (api_tokens hash lookup). Passing the desktop app's fresh
   `access_token` as `SOURCEFOLD_TOKEN` -> every call: "The access token in Claude Desktop isn't valid any
   more". (`mcp-auth.ts` already verifies Supabase JWTs via `auth.getUser` for the remote MCP — reuse that.)
3. The desktop JWT lives ~1 h and only the running app refreshes it (by design, no refresh token is shared).
   With the app closed the borrowed token expires (the one on disk was ~10 h stale when tested).
- Fix: `requireApiUser` accepts a Supabase JWT (verify with `auth.getUser`, apply the ALLOWED_EMAIL check,
  use an RLS client for that user). `loadCredentials` reads the new session shape (web URL = DEFAULT_WEB_URL
  or a new `web_url` field), checks `expires_at`, and when expired returns a clear message
  ("open the desktop app once to refresh the sign-in, or paste an sf_ token"). Consider having the desktop
  app mint/store an `sf_` token for the extension instead so it works while the app is closed.
  Update `manifest.json` long_description and tests (`apps/mcp/src/__tests__/foundation.test.ts`).

### P1-1 get_status says "Signed in" with an invalid/expired token
Local mode reports "Signed in at …, using the access token from Claude Desktop's settings" and then every
call fails. It only checks that a token exists. Fix: validate with a cheap API call and report
"token rejected" in the status. Also the wording says "Claude Desktop's settings" even when the token came
from env in another client (Hermes, Cursor) — say "from SOURCEFOLD_TOKEN".

### P1-2 add_links ignores allow_duplicates=true (remote)
`add_links({allow_duplicates:true})` with an already-saved URL -> "already saved". Check `addLinksRemote`
passes the flag through to the queue/API.

### P1-3 Remote mode advertises desktop features it can never reach
In the web connector the server runs on Vercel, so the desktop bridge (127.0.0.1) is never reachable:
- `get_status` says "Desktop app: not open" even while it is open.
- `find_sources inside_text` and `show_in_app` say "Open the Sourcefold desktop app first" / "needs the
  desktop app to be open" — misleading, opening the app changes nothing.
Fix: in `ctx.mode === "remote"`, report "not available in the web connector" (status: "Desktop app: can't be
reached from the web connector"), hide or reword `show_in_app`, and ideally implement server-side
full-text search (Postgres FTS over item markdown) so `inside_text` works remotely.

### P2-1 remove_text vs highlights
Removing the exact passage that a highlight covers ("Scaled Dot-Product Attention", first occurrence) kept
the highlight listed. The undo description says highlights "go with" the removed text. Verify whether the
highlight was dropped/re-anchored correctly or is now orphaned; make behaviour and docs agree.

### P2-2 undo_remove_text second call gives the wrong reason
After a successful undo, a second undo says "The text … changed since that removal (in the app or by another
removal)". It should say "There is no removal to undo for this source." (the undo row should be dropped
after a successful undo, or the error should be distinguished).

### P2-3 Inconsistent kind label for arXiv
`list_sources` / `get_project_tree` show "arXiv", `list_highlights` and the desktop list show "PDF".

### P2-4 Small text bugs
- "1 links are waiting for your computer" -> pluralize.
- get_add_progress: "saved saved as [...]" (double word).
- queue message: "Try saving it with the Sourcefold extension while you have the page open.. Waiting for the
  Sourcefold desktop app." (double period, and contradictory: extension vs desktop app).
- update_group archive error: `"Sub renamed" is a group in … › Articles › Sub renamed` (path includes the
  group itself; should be its parent path).
- list_cards prints "Section § Intro".
- read_source on an image prints the full signed Supabase storage URL (token in the URL); print the source
  URL or omit the token.
- Length mismatch: read_source says 41,560 chars for the arXiv paper, remove_text says 41,610.

### P2-5 Drive status
get_status: "231 changes not saved yet … last saved 2026-10-19" — the count kept dropping during the session
(231 -> 194) while "last saved" never moved. Check whether automatic Drive pushes run and update
`last saved`, or whether the count is wrong.

### P2-5 finding (not a bug)
`last_saved_at` is written only when a save batch drains the queue completely (`remaining === 0`).
The automatic push (`pushToDriveSoon`) runs a 10-item batch after each save, so the unsaved count
falls while the date stays put until a full drain (a manual `save_to_drive`). The behaviour matches
the code; the wording could say "last fully saved" but that is a copy change, not a defect.
